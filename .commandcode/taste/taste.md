- Appears to work across a monorepo with distinct top-level roots (e.g. `cli`, `source`) and expects the agent to follow the call chain across them (CLI entrypoint → package → core library) to explain end-to-end behavior.
- Writes in a very terse, unpunctuated style and gives instructions in a single burst; expects the agent to fill in intent without asking for clarification up front.
- Proposes the fix themselves in concrete CLI-surface terms (e.g. "can `axiodb serve tcp-auth <password>` so the CLI fires the change on start?"); expects the agent to check the idea against the real code for feasibility and then implement it, rather than bouncing another round of alternative designs back.
- Prefers optional positional arguments for automation-facing commands over interactive prompts/masked input — prioritizes scriptability and re-runnable invocations.
- Wants scope matched tightly to the request: a "simple feature" should touch as few files as possible. Called out "why so many edits for a simple feature" — prefer a small surgical diff over spreading a change across many files.
- Hates scope creep into unrelated/overbuilt extra work (e.g. adding a whole new end-to-end test suite with child-process harnesses). Don't add tests or files that go beyond what the feature itself needs.
- Wants comments minimal: "why added so much useless comments?" — do not write comments that restate the code. Keep only non-obvious *why* comments; match the JSDoc density of surrounding code.
- Tests should live at the layer where the change lives (a CLI feature → a small unit test on the CLI's own code), not a full-stack harness exercising the core library's behavior.

- Bundles several related behavior questions into one message ("is X in Y? also if Z enabled without W? also how does it work in docker?") and expects each answered separately, keyed to the question, grounded in real file/line evidence — not merged into a single narrative answer.
- Audits sibling deployment surfaces for parity: asks how the same feature behaves in Docker/container env-var config and in every client (CLI, cloud client), not just the surface that was changed.

Willing to have the whole pending change set set aside mentally just to understand the starting state.
- Calls out overlong answers as "too complicated & confusing" and narrows the question to one concrete fact (e.g. "what params does the server accept when TCP auth is on?"). Answer with a short list of the actual param names plus a one-line yes/no; skip comparison tables, deep call-chains, and unrequested observations until asked.
