# User Taste Profile
- Expects the assistant to explain and analyze before writing code — applies to reading context ("take context dont code or do action, take context & then tell me"), architectural feasibility questions, and design discussions ("dont code, first tell me"). Always wants to understand implications, tradeoffs, and what would change before any implementation begins. Confidence: 0.95
- Prefers gathering context from multiple files simultaneously before forming a response, rather than sequential single-file reads. Confidence: 0.7
- Prefers structured summaries (tables, bullet points) when reviewing benchmark data or session histories. Confidence: 0.65
- Bundles multi-step tasks in a single message (e.g., "run benchmark → save numbers → create performance page") and expects the assistant to execute the full pipeline without asking clarifying questions at each step. Confidence: 0.85
- Uses very abbreviated, shorthand communication ("rn", "same as previous", dropping articles/pronouns) — expects the assistant to infer full intent from context. Confidence: 0.8
- Expects polished, "beautiful UI/UX" for documentation and presentation pages — values rich visual design (charts, gradients, cards, data tables) over plain layouts. Pushes for improvements even when initial result is "nice" — wants it to "deserve much better." Confidence: 0.85
- Wants data table values to include unit labels (e.g., "ms") rather than raw numbers alone, for readability and clarity. Confidence: 0.85
- Wants contextual metadata included alongside data: machine specs, timestamps, and methodology alongside benchmark numbers. Confidence: 0.7
- Expects comprehensive, exhaustive coverage in benchmark/performance reports — not just a subset of metrics but ALL operation types (CRUD, transactions, HTTP, TCP, crash recovery, etc.). Will ask "do you have all case?" if only a partial dataset is shown. Confidence: 0.8
- Wants benchmark/performance numbers synchronized across ALL project surfaces — when a dataset is updated (e.g., 50K→100K), expects every page referencing those numbers to be updated in lockstep: component pages, llms.txt, llms-full.txt, index.html JSON-LD, SKILL.md, README.md, sitemap, and agent-skills metadata. Expects the assistant to proactively discover and audit every stale reference, not wait for explicit per-file instructions. Confidence: 0.9
- Prefers overview/summary pages to include condensed summaries of subsystems (e.g., test suite grids) with links to dedicated detail pages, rather than duplicating all data inline. Confidence: 0.7
- Prefers live/dynamic data fetched from APIs over hardcoded static values for stats like download counts, pull counts, etc. Explicitly requested npm and Docker numbers be "dynamic from npmjs stats." Confidence: 0.8
- Rejects hardcoded domains in frontend code — expects URLs to use `window.location.origin` so they work on any host (localhost, staging, production). Called out a hardcoded `https://axiodb.in` URL: "why hard coded domain? take the domain current URL." Confidence: 0.9
- Wants platform-specific branding (badges/logos) next to stats to visually identify data sources (e.g., npm logo, Docker logo from simple-icons CDN). Confidence: 0.75
- Prefers consolidating stats from multiple platforms (npm, Docker, GitHub) into a single unified dashboard/section rather than scattered across separate pages. Requested Docker stats shown "near npm one." Confidence: 0.75
- When CORS blocks client-side API calls, insists on SSR (runtime server-side proxy) — not SSG or build-time scripts. Expects a server endpoint that fetches at runtime and sends JSON to the client. Explicitly corrected: "are you mad? i told you SSR not SSG." Also rejected build-time pre-generation: "not build time, fetch server side then send to client side." Confidence: 0.95
- Expects API endpoints organized under a dedicated `api/` folder (file-based routing convention) — not inline route handlers in a standalone server file. Explicitly rejected a monolithic `server.ts` with inline routes: "use /api not this, like under api folder." Confidence: 0.9
- When a feature has gone through multiple failed implementation attempts, prefers to completely scrap and remove it rather than keep iterating: "no no remove that docker one completely." Values clean reverts over incremental fixes on a broken path. Confidence: 0.85
- Cares deeply that documentation/agent-skill content has precise, unambiguous syntax — wants examples that "will not get confused" by end users implementing against the API. Expects comprehensive coverage (core engine + TCP client) in a single skill file so users don't have to piece things together. Confidence: 0.85
- Prefers documentation examples to use realistic multi-machine scenarios (e.g., Machine A with a real IP as server, Machine B as client) rather than localhost-only snippets — wants users to immediately understand the real deployment topology. Asked: "if i want to set my AxioDB A as TCP server & from B want to connect?" Confidence: 0.8
- When crafting copy-to-clipboard prompts for AI agents, prefers instructions that tell the AI to "save" or "fetch and store" the skill/reference, not just "load" it — so the AI can reference it across the session without re-fetching. Explicitly: "instruct ai to save the skill whenever needed this load this." Confidence: 0.8
- Prefers marketing/subtitle copy that leads with competitor pain points (e.g., node-gyp failures, electron-rebuild issues, SQLite C binding errors) before stating the product's solution — Pain → Solution formula, not dry feature lists. Asked to explicitly contrast against SQLite native binding errors and JSON file limitations. Confidence: 0.85
- When asked to write copy, taglines, or persuasive text, expects the agent to web-search best practices and study examples first ("do web search about that how to write a high catchy sub text & then plan then edit") — research-informed content, not just gut-feel writing. Confidence: 0.8
- Prefers brand positioning that is broad and category-defining (e.g., "The Embedded Database for Node.js") rather than narrow "alternative to X" framing — wants the product to own the category, not be defined by a single competitor. Explicitly rejected "SQLite Alternative for JavaScript" as too limiting: "it not be that like, show like why, because it solves not only SQLite issue." Confidence: 0.85
- Wants positioning copy to explicitly name all competitors being replaced (SQLite, LowDB, NeDB, raw JSON) so developers immediately understand the scope — not just "alternative to SQLite" but "Replaces SQLite, LowDB, NeDB & raw JSON files." Confidence: 0.85
- When a brand/positioning change is made, expects a comprehensive sweep updating EVERY surface simultaneously — Introduction.tsx hero, SEO meta tags, Header.tsx descriptions, llms.txt, llms-full.txt, README.md, package.json, Installation.tsx, SKILL.md, agent-skills/index.json, and index.html JSON-LD. Treats this as a mandatory holistic update, not per-file edits. Confidence: 0.9
- Wants badges/shields to be fully consistent across all surfaces — if README has badges, Introduction.tsx (docs site) should have the same full set. Notices when one surface has fewer badges than another and considers it an inconsistency to fix. Confidence: 0.8
- Prefers CLI tools described as just "CLI" without exposing the implementation language (e.g., don't mention Go, Golang, Rust) — the interface matters, not what it's built with. Explicitly: "in cli related things in site dont mentioned Go based or Golang based, just CLI." Confidence: 0.85
- Uses the `gh` CLI tool to manage GitHub repo metadata (description, topics, homepage URL) and expects it to be part of branding/SEO sweeps. Explicitly instructed: "use gh tool in my shell to access the AxioDB repo." Confidence: 0.85
- Wants version numbers kept in perfect sync across ALL project surfaces — uses `package.json` as the single source of truth. Expects a comprehensive grep-and-fix sweep of every file (llms.txt, llms-full.txt, Docker README, docs, README badges, etc.) when a version is bumped or when asked to "sync all versions." Confidence: 0.85
- Wants GitHub repo metadata (description, topics, homepage) included in comprehensive branding updates alongside docs, README, package.json, etc. — not just code surfaces but also the GitHub "About" section and topic tags. Confidence: 0.8
- Notices and flags small numerical inconsistencies between UI-displayed values and badge values (e.g., "32.7K" vs "33K") — wants explanations for discrepancies even when minor. Confidence: 0.7
- When updating test dataset sizes, expects a full unfiltered `npm test` run followed by empirical verification that benchmark numbers match what's published in the docs/numbers.jsonl — not just trusting the numbers, but actually running tests and comparing. Asked: "run npm test, check any failure...then check that the numbers are identical with the docs or the numbers.jsonl or near identical." Confidence: 0.85
- Prefers page section ordering to reflect information priority — wants high-signal sections (download stats, badges) moved UP and niche sections (CLI, detailed docs) moved DOWN. Explicitly asked: "up the number downloads & down the CLI banner." Confidence: 0.75
- When writing social media/LinkedIn posts about project updates, wants a personal story-driven narrative — not structured sections or bullet lists. Prefers flowing paragraphs that tell the origin story (e.g., "I was developing for 1.5 years, got an error with Electron + SQLite, tried alternatives, they were worse, so I built my own"). Wants emojis woven naturally into the text (🚀, ⚡) rather than as section headers or list markers. Explicitly rejected: dividers (━━━), section blocks, bullet-point lists, links, and hashtags. Also explicitly rejected polished/corporate tone — prefers raw, humble language about metrics ("30K downloads, not so much to show off still…"). Wants the post to include tradeoffs, decisions, and GitHub issues/fixes as part of the development journey narrative — not just feature lists. Wants honest positioning about what the project is NOT (e.g., "not like MongoDB, not a traditional DB"). Wants self-deprecating/sarcastic humor as a closing device (e.g., mocking the 2026 AI trend). Wants transparency about what `npm install` actually ships vs what's opt-in. Confidence: 0.9
- Prefers LinkedIn/social media posts to be short and tight — wants anything deemed "nonsense" or filler cut immediately. Iterates by asking to "reduce" and "remove" until the post is lean. Values concise writing that says only what matters over exhaustive feature lists. Confidence: 0.85
- When adding new configurable parameters to an API, insists every param be optional with sensible defaults that preserve current behavior — nothing changes unless the user explicitly opts in. Describes the pattern as: "if user not passed then by default it was activated, also if passed true then ok if false then disable." Generalizes to: all new knobs default to existing behavior, user overrides only what they care about. Confidence: 0.9
- Prefers minimal-touch refactoring approaches over comprehensive rewrites — when presented with two architectural options (e.g., static reconfiguration touching 3 files vs dependency injection touching 10+), approves the leaner path that achieves the same result with fewer files changed. Values backward compatibility and low blast radius in structural changes. Confidence: 0.8
